# Pull Spekit enablement analytics

The Spekit API is **read-only**. Every operation is a `GET` and there is no write path — if the task asks you to change anything in Spekit, this is the wrong tool (use the Spekit MCP connector, `mcp/spekit-mcp.yml`).

## Authenticate

Send the token on every request:

```
Authorization: Token <SPEKIT_API_TOKEN>
```

The literal word `Token`, a space, then the token. The token is generated by a Spekit **Account Admin** in the web app under **Settings → API Tokens**, with an expiry the admin chooses (one week through never-expire). It is shown once at generation and cannot be retrieved afterwards. If you do not have a token, stop and ask for one — do not attempt anonymous calls.

## The five operations

| operationId | Path | Returns |
|---|---|---|
| `v1_users_list` | `/v1/users/` | Org users with `id` (uuid), `first_name`, `last_name`, `email`, `is_active`, `created_on`, `teams[]` (team + role) |
| `v1_analytics_searches_list` | `/v1/analytics/searches/` | Each search: `user`, `keywords`, `source`, `created_on` |
| `v1_analytics_speks_views_list` | `/v1/analytics/speks/views/` | Each view: `user`, `spek` (id, link, type_short, label, deleted), `view` (id, source, user_action, created_on), `associated_teams[]` |
| `v1_analytics_speks_reactions_list` | `/v1/analytics/speks/reactions/` | Each reaction: `user`, `spek_name`, `spek_link`, `spek_type`, `reaction`, `created_on` |
| `v1_analytics_user_activities_list` | `/v1/analytics/user-activities/` | Each activity: `user`, `activity_type`, `activity_id`, `ip`, `created_on` |

## Page correctly

Every response is the same envelope: `{count, next, previous, results[]}`.

1. Request the first page with `page_size` (default 50, **maximum 100** — a larger value is not honoured).
2. If `next` is non-null, request that URL verbatim. It already carries the opaque `cursor`; do not construct the cursor yourself.
3. Stop when `next` is null. Do not rely on `count` to decide when to stop — page until `next` is null.

## Filter by time

`v1_analytics_searches_list`, `v1_analytics_speks_views_list`, `v1_analytics_speks_reactions_list` and `v1_analytics_user_activities_list` accept `start_date` and `end_date` as RFC 3339 date-times. Always send both for a reporting pull — an unfiltered analytics call pages the whole history and will hit the rate limit.

`v1_users_list` has **no** date filter. Page it whole.

## Filter the activity feed

`v1_analytics_user_activities_list` takes `activity_type`, one of 21 values: `api_auth_token_generated`, `api_auth_token_revoked`, `asset view`, `files_uploaded`, `flow_completion`, `flow_created`, `flow_start`, `knowledge_check_attempt`, `knowledge_check_created`, `knowledge_check_question_attempt`, `marked_asset_read`, `marked_spek_read`, `reaction`, `recommendation`, `search`, `spek view`, `spek_created`, `spotlight_completion`, `spotlight_created`, `team_created`, `topic_created`. Omitting it returns all types.

Note the two with spaces — `asset view` and `spek view` — and URL-encode them.

`activity_id` is an opaque pointer into the record the activity describes. The per-type payload shape is documented in the operation description in the spec, **not** in `components.schemas`, so there is no typed model for it. Read the description before interpreting `activity_id`.

## Respect the limit

- **30 requests / 10 seconds.** Short bursts are tolerated; sustained excess returns `429`.
- There is **no** `Retry-After` and **no** `RateLimit-*` header — you get a bare 429 and nothing else. Implement exponential backoff on your own clock, starting at ~2s and doubling.
- Throttle proactively: pace to roughly 3 requests per second rather than bursting and recovering.

## Errors

The spec declares **only** `200` responses — there are no error schemas. Treat non-200 by status code alone:

- `401` — the token is missing, malformed (missing the `Token ` prefix), expired, or revoked. Do not retry; get a new token.
- `429` — back off exponentially and resume.
- anything else — surface the raw status and body; there is no documented error envelope to parse.

## Joins to know about

- Every analytics record embeds the full `User` object. You do not need a second call to resolve a user.
- Views carry a `spek` object with an `id`; reactions carry only flattened `spek_name` / `spek_link` / `spek_type` strings. **You cannot join reactions to views by spek id** — join on `spek_link` if you must, and say so in the output.
- Spek **bodies** are never returned by this API. Only ids, labels, links and types. Reading content requires the MCP connector.
